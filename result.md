## 2. Faults found in the existing project

These bugs were already in the code before this work:

1. **The Docker image could not build.** `npm ci --omit=dev` ran the `husky install` script, but
   husky is a dev dependency → `husky: not found`.
2. **The container would crash at startup even if it built.** The server imports `dotenv`, which
   was only a dev dependency.
3. **Blank page in Docker.** The frontend needs the Supabase URL and key at *build* time, but
   `.env` is excluded from the image, so they were never passed in.
4. **The database was unreachable from Docker.** The direct Supabase host
   (`db.<ref>.supabase.co`) resolves to an IPv6 address only, and Docker has no IPv6. This is the
   most likely cause of the team's "Docker/localhost doesn't work" problem.
5. **Secrets in the public repository.** `.env.example` contained what looked like the real DB
   password, JWT secret and Sentry DSN.
6. **The QR code pointed to the wrong place.** It encoded the external link, not the product
   passport, and it was generated by a third-party website.
7. **Editing a product could wipe data.** The edit form never loaded the three warnings,
   saturates, sugar, protein or salt, so saving showed them empty and could overwrite them.
8. **The phone menu was missing.** Navigation links were hidden below 768 px with no replacement.
9. **The products table clipped on phones.** Nine columns sat inside `overflow-hidden`.
10. **Menu hovers were dark green.** The shared `accent` token, which shadcn uses for hover
    backgrounds, was set to a dark green.
11. **Redirect Link was not implemented.** The form offered it, but the public page ignored it.
12. **Smaller gaps:**
    - no way to attach ingredients to a product
    - no loading or empty states on lists
    - icon-only buttons with no labels for screen readers
    - the Edit button on the product page was commented out

## 3. Problems faced during the work

| Problem | What happened | How it was handled |
|---|---|---|
| Google Drive connector | Authentication failed when reading the DPP doc | Read the shared doc through its public text export instead |
| Docker daemon | Docker Desktop was not running, so the first build failed to connect | Started Docker Desktop, waited for the daemon, rebuilt |
| Supabase over IPv6 | The container could not resolve the database host | Confirmed with a DNS lookup (IPv6 address only). Fix: Session pooler URL (IPv4), now documented in `.env.example` and the README |
| Finding the pooler region | A probe that tried the stored password against many regions was blocked by the safety guard | Not attempted again. The team copies the exact pooler URL from the Supabase dashboard |
| Testing without touching production data | Writes could have hit the shared Supabase DB | Ran a throwaway local Postgres container with seed data and pointed the real Docker image at it |
| Admin pages need a real login | Screenshots of logged-in pages were impossible with a real account | In the test script only: a fake browser session plus API responses built from the real public endpoint. App code was not changed for this |
| Shell quoting | Two long edit scripts broke on nested quotes | Wrote the scripts to files and ran them |
| Playwright browser | The headless build was not installed | Used the installed full Chromium build instead of downloading another |
| Label download did nothing | The download link's object URL was revoked immediately after the click, which cancels the download in Chromium | Attach the link to the page and revoke the URL later. Download verified |
| Label layout overlaps | The warning pictograms overlapped the producer line, and the QR caption ran past the label edge | Re-spaced the fixed zones and shortened the caption. Checked again in screenshots |
| Overflow on phone detail page | A truncated link inside a grid column forced the page to 398 px | `min-w-0` on the grid columns. The automatic overflow check now passes |
| "Château" garbled in output | Looked like an encoding bug | Checked the bytes in the database and in the API response: both correct UTF-8. It was only the Windows console. No change needed |

## 5. Added to the project without changing existing behaviour

These are purely additive. Existing data, endpoints and flows keep working as before:

- **Database:**
  - the nullable column `products.ingredient_ids` (existing products are unaffected)
  - the new `scans` table
  - an additive, re-runnable SQL migration
- **New endpoints:**
  - `POST /api/public/scans`
  - `GET /api/scans.geojson` (off unless `SCANS_EXPORT_KEY` is set)
  - a `publicUrl` field added to `/api/config`
- **Existing endpoints** return one extra field, `ingredients`. Nothing is removed or renamed.
- **New components:** `WineLabel` (label + QR + SVG download) and `IngredientPicker`.
- **Image upload fallback** to the local volume, used *only* when no Vercel Blob token is configured.
  With a token, behaviour is unchanged.
- **New files:**
  - `docker-compose.yml`
  - `npm run check:storage` (test-database check)
  - docs (README, `tasks/`, `implementation.md`, `result.md`, screenshots)
- New npm packages: `qrcode` (+ types). `dotenv` was moved, not added.

Deliberate behaviour changes (so nobody is surprised):
- The QR code now opens the product passport instead of the external link.
- The product detail page is one page instead of tabs.
- The public page hides empty sections.
- The public page now honours Redirect Link.
- `Dockerfile.new` is deleted.

## 8. Known limits

- Label text wrapping estimates character width; very long ingredient lists are cut at 5 lines on the
  label (the full list is always on the passport page).
- The exported SVG names the fonts but does not embed them, so on a machine without Gloock and
  Public Sans it falls back to Georgia/Arial.
- The scan endpoint's rate limit (60 per IP per minute) lives in memory: it resets on restart and
  is per container. Behind a reverse proxy, every request shares the proxy's IP.
- Sentry reports browser errors only; the production server (`server/production.ts`) does not
  initialise it.
- If no public address is configured, the QR fallback is the fixed Render address
  (`PRODUCTION_URL` in `client/src/components/label/WineLabel.tsx`). Update it if the site moves.
- The DPP document's wider goals are not started: role-based views (business, repair, authority),
  GS1 Digital Link URLs, and version history/provenance. The "next task" in the doc (studying
  open-dpp and tractusx) is research, not code.

## 9. Demo script (evening meeting)

1. Landing page: the sample label is the hero.
2. Log in → Products → open a product → the **Bottle label** panel → download the SVG.
3. Scan the label's QR with a phone → public passport page → allow location.
4. In the product form, click **Auto-fetch location** → the address fills in → **Preview on map**
   opens Google Maps.
5. `docker compose ps` → the container is shown as healthy (or Render's health check is green).
